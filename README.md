# restore-rsi

把 JarvisIR 式的图像复原工具箱接进 [reef](https://github.com/Human-Agent-Society/reef) 的自进化(harness evolution)循环,
跑通,然后**把这个循环自己的评估机制拆开量了一遍**。

纯 CPU,零 GPU:6 个确定性经典算子(DCP 去雾 / gamma+CLAHE 提亮 / 双边+中值去噪 / unsharp 锐化),
模型只用来提议策略。所有数字都能在这个仓里复现。

> 这个仓的重点不是"复原效果",是**循环里那个判断"这条经验该不该留下"的闸门可不可信**。

---

## 结论

1. **闸门原来的判据是抛硬币。** reef 自带规则是"胜数 > 负数";候选和现版没差别时,
   每次逐题比较就是一次抛硬币,而"正面多于反面"本来就有 50% 概率 —— 跑多少次重复都改不掉。
   换成符号检验后重判真实发生过的四步,**当时发布的 3 条经验没有一条经得起检验**。
2. **观测和奖励的缺陷能修好,修好之后策略行为明显变对** —— 有行为侧实测。
3. **真正的瓶颈是"何时收手"**:它值 23% 的可达分数,而**一条十行的确定性规则已经比 LLM agent 做得更好**。
   自进化循环现在想学的东西,基线已经超过它了。

### 1. 闸门:从未定义的错误率,到已知的错误率

| 那一步 | 胜/负 | 旧判据 | 符号检验 | 单侧 p |
|---|---|---|---|---|
| 首轮 step1 | 2/1 | 发布 | **拒绝** | 0.500 |
| 首轮 step2 | 2/1 | 发布 | **拒绝** | 0.500 |
| 干净轮 step3 | 3/0 | 发布 | **拒绝** | 0.125 |
| repeats 轮 | 4/5 | 拒绝 | 拒绝 | 0.746 |

这不是"把闸门调严",是**把它的错误率变成已知量**:旧规则不是宽松,是从未定义过错误率。

推论:每题只评 1 次时 n=3,即使 3 胜 0 负也只有 p=0.125,**永远达不到门槛**。
所以"每题重复评估"不是优化,是闸门能发布任何东西的前提(现在 `repeats: 3`,每一步自带可靠性读数)。

### 2. 观测与奖励:两个便宜的探针,任何 RSI 系统可复用

- **读数互相污染**:同一张图同样的雾,只是加了暗光,雾读数掉 91%;而"模糊"在**干净参考图上就读 0.912**
  (它测的其实是"梯度能量低")。修法是让每个读数在"其他退化已被抵消"的图上测。
- **奖励刻度截断**:原刻度下限 15 dB **高于任务起点**(三个评测任务是 13.19 / 12.76 / 8.59 dB),
  39% 的 episode 分数钉死在 0,单工具几乎全 0 → agent 的第一步永远拿不到反馈。改成相对退化输入的改善量。
- **行为侧硬证据**(任务名已换成不可读哈希,所以只能归因于诊断变准):
  锐化调用 23.7%→5.8%(任何最优链都不含它)、去雾 9.2%→17.3%(含雾题最优链的第一步)、提亮 20.8%→40.4%。

### 3. 停手:3096 个决策点的穷举

动作可枚举 + 任务有真值,所以能穷举所有链的每一步,把"agent 看得见的观测"和"真实分数变没变好"配对。

| 盲信号 | AUC |
|---|---|
| **试走一步后诊断总分的下降量** | **0.789** |
| 试走后的诊断总分 | 0.650 |
| 已偏离输入多远 | 0.608 |
| 模糊 / 链长 / 雾读数下降量 | 0.43–0.49(抛硬币) |

被发布的那条 skill 教的规则("读数降了就说明这步对")**精确率只有 57.2%**;调阈值最高 71.7%,而召回掉到 24.8%。

而十行确定性贪心(每步试走 6 个工具、选诊断降幅最大的、降不动就停)在 12 题上合计 **5.6092**,
同一轨迹上出现过的最高分合计 **7.2625** —— **"不知道该在哪停"值 23% 的可达分数**
(`noise_01` 走过 0.8276,最后停在 0.0568)。三个评测任务上贪心拿 **0.607 / 0.267 / 0.649**,
比 LLM agent 的典型 episode 好,**而且从不归零**(agent 在 0.0–0.57 之间跳)。

**这个开放问题和"无参考指标可靠性"是同一件事**:盲策略没有分数,诊断测的是"还剩多少退化"
而不是"离原图多远",过度处理时读数继续降而图在变差。


## 工具层:6 个能跑的,12 个在册待接

`toolbox/registry.yaml` 里现在有 18 个工具,三种后端:

| 后端 | 数量 | 在哪跑 | 状态 |
|---|---|---|---|
| **builtin** | 6 | 本进程 | 可跑。DCP 去雾 / gamma + CLAHE 提亮 / 双边 + 中值去噪 / unsharp 锐化 |
| **docker** | — | 本机容器 | 依赖隔离用:12 个专家模型来自 12 篇论文,torch/basicsr 版本互相冲突 |
| **remote** | — | 任意一台机器 | 循环和卡不必在一起 |
| *(JarvisIR 专家模型)* | 12 | — | 在册,`enabled: false`,等权重和卡 |

加工具只改这个 yaml,不改代码。**三种后端都是一进一出**,所以换后端时循环、缓存、
trace、闸门一行都不用动。

### 循环和卡可以不在同一台机器上

真专家模型要 GPU,而 GPU 未必是跑循环那台。所以工具在哪是一个**配置**:

```bash
# 在有卡的机器上起服务
python -m toolbox.server --port 8710

# 循环那侧只改一个环境变量
RESTORE_TOOL_SERVER=http://127.0.0.1:8710        # 同机,零网络
RESTORE_TOOL_SERVER=http://<tailnet-ip>:8710     # 跨机
```

这个形状不是凭空来的:JarvisArt 也是因为 Lightroom 只能跑在特定机器上,才做了
Agent-to-Lightroom 的 server-client 协议来支持多机多卡。

**执行位置不是一个自由变量**,这一点是测出来的而不是假定的:同一个算子经 HTTP 跑一遍,
输出与本机直接跑**像素完全相同**(`tests/test_remote_backend.py` 真起一个服务来验,
不 mock)。它一旦不成立,之前所有跨机器跑出来的数字就不能和本机的比 —— 那正是
"拿两个数比大小却没先确认可比性" 的又一个入口。判据的灵敏度也验过:让服务端悄悄
改一个像素、差 1,测试立刻红。

**两种后端的路径纪律相同**:docker 只让容器看到 `input.png`,remote 只发字节不发文件名。
理由见下面第 5 条。

```bash
restore doctor      # 逐个验证声明的工具此刻是否真能跑(remote 会去问服务端)
restore catalog     # agent 看到的目录,只列可跑的
```

### 为什么要有 `enabled` 和 `doctor`

因为"声明了"和"能跑"是两件事,而它们的差如果不显式,就会变成训练信号里的噪声。

JarvisIR 的 `ALL_TOOLS` 有 13 项,模型被告知都能选,但 `restormer` 既没有
`process_image_with_models` 里的执行分支,也不在 `all_model_paths` 里。选中它会走
`print(...)` + `continue`:链继续往下,最后返回一个"处理过"的路径,reward 照常计算。
于是 **"这个工具没用" 和 "这个工具没接上" 在训练信号里完全不可区分**,而模型只会学到前者。

所以这里:未启用的工具不进 `catalog`;`restore run` 调用它会**非零退出**并报
`disabled_tool`(与打错名字的 `unknown_tool` 分开报,因为要人做的事不同);
`tests/test_tool_registry.py` 把"启用的工具必须真能跑"钉成仓库级不变量。
验证过它能亮红:把 `ridcp` 标成 `enabled: true`(镜像并不存在),不变量测试立刻指名它,
`doctor` 退出码变 1。

## 七条工程纪律(这个仓踩出来的)

1. **不静默降级。** "我没测出来"和"它什么都没做成"是两件事,而后者是会决定胜负的真分数 ——
   2026-09-03 两次 `select` 判决都压在一道恰好 0.0 的题上,其中至少一次是测量失败。
   现在 judge 侧的测量失败一律抛错(`tests/test_measurement_failures.py` 守着,
   并且同时守住反向判据:**合法的 0.0 必须仍然是 0.0**)。
2. **判据从被测代码原样抄,不自己重推。** 天花板必须用闸门自己的度量来量,
   所以 `oracle_chains.py` 直接调 `restore score` 用的那两个函数。
3. **声明不等于可用,而这个差必须显式。** 见上一节:一个在册却不能跑的工具,
   会让 agent 学到"它没用",而不是"它没接上"。
4. **测试不只会变红,它还会消失。** 干净 clone 上 `pytest -q` 曾打印
   `144 passed, 27 skipped` 并**退出码 0** —— 因为 `tasks/data/` 是 gitignored 的生成物,
   而生成脚本曾硬编码 `sys.path` 到仓外。所以 CI 的判据不是"退出码 0",
   是"跳过的数目等于我说好的那个数"。
5. **"失败"要相对这道题能达到什么来定义。** `data.max_score` 是一把绝对尺子(0.5),
   而这 12 道题穷举出来的上界差 **46.5 倍**(0.0215 ~ 1.0000)。实测 12 题里 4 题判反:
   `low_light_00` 上界 1.000 只拿到 66%,绝对阈判"成功"于是**永不进 batch**;
   `haze_noise_00` 上界 0.202 拿到 113%,绝对阈判"失败"于是进 batch,让 propose
   去为一道已做到头的题找不存在的改进。**batch 的组成因此系统性地偏了**,而挪阈值
   救不了 —— 一把尺子量不了 46 倍的量程。现在报的是达成率,绝对分和上界留在 feedback 里。
6. **给 propose 看它需要诊断的东西,不是结果。** 它原来只拿到任务描述、分数,和一句
   `chain=sharpen>gamma`,于是只能凭任务描述猜策略。现在从 trace 重建观测-动作序列,
   它能看到"在雾读数 0.317 的图上第一步选了锐化"这种可诊断的错误。第一次接上就看出
   一件以前看不见的事:agent 只在第一步诊断过一次,后面两步都是盲动 —— 而不重新诊断,
   就无从知道该不该收手。
7. **别让路径名替 agent 做决定。** JarvisIR 的 `process_image` 在输入图片路径里
   grep `"fog"` / `"night"` / `"snow"` 来决定哪些工具可用,而数据集按场景命名目录是
   常规做法 —— 于是"该用哪个工具"有一部分是路径给的,不是模型学的。这个仓为此把
   任务 id 换成了不可读哈希(改完锐化调用从 23.7% 掉到 5.8%),docker 后端也只让
   容器看到 `input.png`,不留第二条通道。
